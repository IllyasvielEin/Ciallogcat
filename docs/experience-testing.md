# 原生场景体验方案

目标：验证一个 Android 开发者或 Agent 能否完成「复现 → 定位 → 核对上下文 → 保存证据 → 交接」，并找出单元测试难以描述的操作阻力。体验使用实际 GUI/CLI 二进制；设备协议和日志内容可以由 mock ADB 提供。

已执行范围及局限见[验证摘要](validation.md)；后续验收见[TODO](../TODO.md)。

## 方法依据与边界

2026-10-23 查阅以下方法资料：

- [NN/g：Task Scenarios for Usability Testing](https://www.nngroup.com/articles/task-scenarios-usability-testing/)（2014-01-12）：任务应真实、可行动，给目标和背景，避免告诉体验者点哪里。
- [GOV.UK：Using moderated usability testing](https://www.gov.uk/service-manual/user-research/using-moderated-usability-testing)（页面更新 2017-10-03）：先明确研究问题和参与者，记录实际操作与恢复；使用虚构数据时承认上下文投入的差异。
- [NN/g：Synthetic Users](https://www.nngroup.com/articles/synthetic-users/)（2024-06-21）：模型生成的偏好与体验不能替代真实用户研究。该文主要评价访谈/问卷式模拟，不是对本项目原生自动化结果的测评。

本轮让模型代理通过键鼠、窗口和文件完成任务，能提供可复现的软件行为证据；模型的判断仍不能代表人类的认知、习惯、疲劳或偏好。记录实际命令、截图、文件与身份校验，不使用虚构的 SUS、满意度、人体工学评分，不把工具调用墙钟时间当成人类任务时间。

## 三个任务包

| 任务 | 交给体验者的背景与结果要求 | 主持人核对 |
| --- | --- | --- |
| 在线故障复现 | com.example.shop 结算后转圈并失败；自行接入设备、复现、解释原因，交出同事可以复核的证据；随后遇到发现失败与流中断 | 是否找到相关请求与原因、排除其他应用同词噪声；区分浏览/停止采集/断流；恢复后身份与旧记录是否正确 |
| 离线事故交接 | 无设备，只拿到一份崩溃记录；找前因、完整长消息和堆栈，导出可复核片段；另一份文件不完整 | 是否越过预览读取全文；证据保留来源和必要上下文；坏文件/取消/已存在目标是否损伤当前阅读状态 |
| Agent 排障与人机交接 | 使用 CLI 围绕外部操作建立有限会话，查询原因与上下文，取回全文；断线后继续取证，最终交给 GUI | 是否遵守字节预算与分页；空结果是否误判；明确 partial/gap；同一 session/seq 能否在 GUI 核对 |

首轮任务描述不包含故障答案、按钮坐标或操作步骤。可阅读公开用户文档，但必须记录阅读发生在操作前还是遇阻后。两名 GUI 体验者首轮不读源码、mock oracle 或其他报告；场景作者参与的 Agent 流程是契约验证，不计作盲测。三名代理都是模型，角色任务不同不代表三个人群样本。

首轮之后才进入诊断与交叉复现：其他代理或主持人用新配置重现，必要时读源码定位。复现所用版本不变。若之后修复，使用另一个二进制摘要重跑受影响任务，避免把原始发现与修复结果混在一起。

## 可控场景与运行隔离

[体验实验工具](../tools/experience-lab/README.md)提供独立 stdlib mock ADB、准备工具和原生会话控制器。mock 包含多进程背景日志、关联请求、重试、其他应用的误导性 timeout、Unicode、预览外的长诊断、进程重启和断线恢复；text 与 proto 共用合成业务记录，但 proto 独立编码。

- 每位体验者独立状态、配置、证据文件、trace、X11 显示和剪贴板。
- GUI/CLI 使用冻结副本，保存 SHA-256；依赖下载后只解包进测试目录，不安装系统软件。
- Xvfb 放在私有挂载/网络命名空间中；不连接或操作用户正在使用的桌面。软件绘制能验证窗口布局与输入主路径，不测 GPU 帧延迟。
- 通过 `init/checkout/crash/offline/online/discovery-error/discovery-ok/quiet/recover/stop` 控制场景；不会执行真实 adb、点击真实手机或访问真实服务。
- 业务事件仅发送给已开启的流。流和 GUI 会话分别有 10/30 分钟 watchdog，测试结束显式停止采集并回收自建进程。
- 真值 `oracle.json` 只供主持人核对；答案必须来自产品展示或导出的证据。输入工件保留生产命令、哈希和版本。

系统 IME、窗口管理器、门户对话框、真实多显示器 DPI、GPU 呈现和 Android USB/厂商行为另做真实环境验收。本方案不能把这些条件模拟成“通过”。

## 记录格式

每个任务至少保留：

1. **前提**：二进制摘要、窗口尺寸/DPI、场景种子或动作序列、已读文档、是否看过源码/答案。
2. **逐步观察**：目标 → 实际动作 → 可见反馈 → 判断 → 遇阻后的恢复；关键步骤有截图和时间戳。
3. **结果**：得到的结论、session/seq 或 artifact-local 身份、导出范围、文件哈希、是否完成/借助文档完成/未完成。
4. **问题**：触发条件、期望与实际、影响、复现次数、证据、建议；区分产品缺陷、体验摩擦、自动化/主持失误、未覆盖项。

默认输出在忽略目录 `target/experience-2026-10-23/`。不要把测试日志和截图误当产品遥测。完整动作记录便于复核，不据此把每个点击都固化成脆弱的 CI 坐标脚本。

## 从体验问题到回归

优先级依次考虑证据错误/数据损失、无法完成关键任务、反复需要绕路、轻微文案或布局阻力。每项同时标明证据强度：独立复现、单次观察、待验证假设。三个模型一致评价不等同于统计显著性。

稳定的协议、状态和文件失败模式进入确定性测试；少量真实窗口启动检查进入 CI；发现、取舍、完整任务和键鼠阅读保留为人工/代理体验脚本。真实 Android 开发者应另做无操作提示的任务体验，重点验证模型不可靠的人类可发现性与负担。
